# 설계: 첫 프레임 뒤 멈춤 — 원인 측정 (issue #6)

## 1. 측정된 사실 (확인됨)

* 조건: reDMP2 v0.0.3(lift 패치 `0007`/`0008`) + repsp `i69-poll-timeouts`(시간이 지난 대기를 안전점에서 깨움). `redmp2 roms --headless --max-vblanks 600`.
* 표시 1프레임, `sceDisplayWaitVblankStart` 0회. 600 vblank 제한으로 정상 종료(정지 분류 (e)).
* repsp #69 전에는 사운드 스레드(`0x0882FAE4`, 우선순위 18)가 첫 `DelayThread` 뒤 굶었다. #69 뒤에는 600 vblank 동안 `__sceSasCore` → `sceAudioOutputPannedBlocking` → `sceKernelDelayThread(100)`을 1,738번 반복한다(언더런 0). 이것은 실제 버그였고 고쳐졌다. 그러나 멈춤은 그대로다.
* `REPSP_HLE_TRACE`: 사운드 스레드를 만들고 시작한 직후부터 `user_main`(우선순위 32)이 `sceKernelSetEventFlag(0x11, 0x2)`만 7,200만 번 부른다. 인자는 매번 같다. 이벤트 플래그 `0x11`은 사운드 초기화 중 `sceKernelCreateEventFlag(attr 0x200, init 0)`로 만들어졌다. `Wait`/`Poll`/`Clear`/`Refer` EventFlag 호출은 어느 스레드에서도 0회다.
* `SetEventFlag`를 부르는 곳(생성 코드)은 `0x0880B960` 한 곳과 `0x0882DF50..0x0882F384` 여러 곳이다. 뒤쪽은 사운드 스레드 진입점과 같은 사운드 라이브러리 영역이다.

## 2. 가설 (추정)

* H1: `user_main`이 사운드 라이브러리에 명령을 보내고(`SetEventFlag(ef, 2)`), 사운드 스레드가 처리했다는 표시(공유 메모리 값)를 바쁜 대기로 기다린다. 사운드 스레드는 돌지만 명령 처리 경로로 들어가지 않는다. 그 분기를 정하는 값이 HLE 반환값(예: `__sceSasCore`, `sceAudioOutputPannedBlocking`의 반환값 `0x100`, SAS 보이스 상태)이나 아직 부르지 않은 HLE의 부작용에 달려 있을 수 있다.
* H2: 반복문 조건이 인터럽트·콜백(`sceGeSetCallback`으로 등록한 GE finish/signal 콜백, vblank 인터럽트)이 바꾸는 값이다. GE 리스트 2개가 끝났는데 콜백이 불리지 않았거나 다른 인자로 불렸을 수 있다.

## 3. 측정 방법 (이번 단계)

고치기 전에 원인을 측정으로 확정하고 보고한다.

1. 반복문을 특정한다: 바쁜 반복에서 `SetEventFlag`를 부르는 호출 위치(`$ra`)와 그 반복문이 매번 읽는 메모리(조건 값의 주소). 방법은 구현에서 고른다. 예: `REPSP_HLE_TRACE`에 호출자 `$ra`를 더하는 진단(repsp, 진단 전용), `REDMP2_TRACE_GUEST` 빌드의 게스트 함수 진입 기록, crash capture의 최근 실행 고리 버퍼.
2. 그 조건 값을 누가 써야 하는지 찾는다: 같은 주소에 쓰는 게스트 코드(생성 코드 검색은 위치 후보를 찾는 데만 쓰고, 실제로 쓰이는지는 실행으로 확인), 그 코드가 실행되지 않는 이유(어느 분기에서 갈리는지, 그 분기가 읽는 값과 그 값의 출처 HLE).
3. 결과를 `docs/analysis/boot.md`에 확인됨/추정/미확정으로 적고 보고한다. 수정은 원인이 확정된 뒤, 그 결과에 따라 repsp issue 또는 이 저장소에서 따로 정한다.

* 진단 코드는 기본 빌드에서 비용이 없어야 한다(환경 변수 또는 CMake 선택 사항). repsp에 넣는 진단은 repsp #69의 범위가 아니므로 필요하면 리드에게 먼저 보고한다.

## 4. 검증

* 측정 명령과 출력 요약이 작업 로그에 있고, 다시 실행해 같은 결과가 나온다.
* 생성 코드 없이 CTest 30/30(CI 조건). 진단을 넣었으면 꺼진 상태에서 동작과 성능이 같다.

## 5. 원인 (확인됨)과 수정

* 측정(`REDMP2_TRACE_NID`, 커밋 `76989e5`): 모든 `sceKernelSetEventFlag(0x11, 2)`의 `$ra`는 `0x0882FB74`다. 원본 MIPS에는 바쁜 대기가 없다. `0x088312C8`은 `$a0`/`$a1`을 정하고 `j 0x0882E618` → `j 0x088C0540`(import stub)으로 한 번 꼬리 호출하고 `$ra`로 돌아가야 한다. H1·H2는 기각.
* 결함: 생성 코드 `psp_body_088312C8`에서 `L_0882E618: psp_import_088C0540();` 뒤에 `return;`이 없어 아래 `L_088312C8:`로 흘러 내려가고 `goto L_0882E618;`로 무한 반복한다. `emit.c`의 `j` 경로가 `if (!c->trampoline || !is_function(an, in.target)) return;`인데, 트램펄린 모드에서 대상이 import stub이면서 함수 목록에도 있으면 `return;`을 빠뜨린다(`PSP_TAIL`은 스스로 돌아오지만 import 호출은 아니다). 이 조건은 로컬 패치 `0005-emit-trampoline.patch`(upstream PR #37)에서 왔다. 같은 형태 13곳 중 12곳은 함수 끝 `}` 앞이라 우연히 맞게 돌아온다.
* 수정 1 (새 패치 `0009`): `j`의 대상이 import이면 항상 `return;`을 낸다. 같은 조건을 쓰는 다른 꼬리 호출 경로(조건 분기의 꼬리 등)도 확인한다. `0005`는 PR #37과 같게 둔다.
* 수정 2 (조사 후 결정): import stub `0x088C0540`이 왜 함수 목록에 들어갔는지 확인한다(`0007`의 lui+addiu 스캔이 stub 주소를 진입점으로 넣었을 가능성, **추정**). 원인이 우리 패치면 그 패치에서 stub을 걸러낸다(`0008`처럼 `is_import_stub`).
* 확인: 13곳 모두 `return;`이 있는지 생성 코드 검사, `lift_audit.py`, reDMP1 비교(같은 결함이 있는지 포함, 읽기만), 헤드리스 실행의 표시 프레임 수와 다음 정지.

# Design: stall after the first frame — measuring the cause (issue #6)

## 1. Measured facts (confirmed)

* Setup: reDMP2 v0.0.3 (lift patches `0007`/`0008`) + repsp `i69-poll-timeouts` (expired timed waits wake at safe points); `redmp2 roms --headless --max-vblanks 600`.
* One frame presented, `sceDisplayWaitVblankStart` called 0 times; a clean exit at the 600-vblank limit (stop class (e)).
* Before repsp #69 the sound thread (`0x0882FAE4`, priority 18) starved after its first `DelayThread`. After #69 it runs `__sceSasCore` → `sceAudioOutputPannedBlocking` → `sceKernelDelayThread(100)` 1,738 times in 600 vblanks (no underruns). That was a real bug and is fixed, but the stall remains.
* `REPSP_HLE_TRACE`: right after the sound thread is created and started, `user_main` (priority 32) calls only `sceKernelSetEventFlag(0x11, 0x2)`, 72 million times, with the same arguments every time. Event flag `0x11` was created during sound initialization by `sceKernelCreateEventFlag(attr 0x200, init 0)`. No thread ever calls `Wait`/`Poll`/`Clear`/`Refer` EventFlag.
* The call sites of `SetEventFlag` in the generated code are `0x0880B960` and several in `0x0882DF50..0x0882F384`; the latter are in the same sound library region as the sound thread's entry.

## 2. Hypotheses (inferred)

* H1: `user_main` posts a command to the sound library (`SetEventFlag(ef, 2)`) and busy-waits for a shared memory value saying the sound thread processed it; the sound thread runs but never takes the command path. The branch that decides it may depend on an HLE return value (for example `__sceSasCore`, `sceAudioOutputPannedBlocking` returning `0x100`, SAS voice state) or on a side effect of an HLE not called yet.
* H2: the loop condition is a value changed by an interrupt or callback (the GE finish/signal callback registered with `sceGeSetCallback`, the vblank interrupt); the two GE lists finished but the callback may not have run, or ran with other arguments.

## 3. How to measure (this step)

Establish the cause by measurement and report it before fixing anything.

1. Pin down the loop: the call site (`$ra`) of `SetEventFlag` in the busy loop, and the memory the loop reads each time (the address of the condition). The implementation picks the method, for example a diagnostic adding the caller's `$ra` to `REPSP_HLE_TRACE` (repsp, diagnostics only), guest function-entry records in a `REDMP2_TRACE_GUEST` build, or crash capture's ring buffer of recent execution.
2. Find who should write that value: guest code writing that address (searching generated code only finds candidates; whether it runs is checked by running), why that code does not run (where the branch splits, what value it reads, and which HLE that value comes from).
3. Record the result in `docs/analysis/boot.md` as confirmed/inferred/unresolved and report. The fix is decided once the cause is confirmed, as a repsp issue or here.

* Diagnostics cost nothing in the default build (an environment variable or a CMake option). A diagnostic in repsp is outside repsp #69's scope; if one is needed, report to the lead first.

## 4. Verification

* The measurement commands and output summaries are in the work log, and re-running gives the same result.
* CTest 30/30 without generated code (the CI condition); any diagnostic, when off, leaves behaviour and performance unchanged.

## 5. Cause (confirmed) and fix

* Measured (`REDMP2_TRACE_NID`, commit `76989e5`): every `sceKernelSetEventFlag(0x11, 2)` has `$ra` `0x0882FB74`. The original MIPS has no busy wait: `0x088312C8` sets `$a0`/`$a1`, tail-calls once through `j 0x0882E618` → `j 0x088C0540` (an import stub) and should return to `$ra`. H1 and H2 are rejected.
* Defect: in the generated `psp_body_088312C8`, `L_0882E618: psp_import_088C0540();` has no `return;` after it, so it falls into `L_088312C8:` and loops through `goto L_0882E618;`. `emit.c`'s `j` path is `if (!c->trampoline || !is_function(an, in.target)) return;`; in trampoline mode a target that is an import stub and also in the function list loses its `return;` (`PSP_TAIL` returns by itself, an import call does not). The condition comes from local patch `0005-emit-trampoline.patch` (upstream PR #37). Of the 13 sites of this shape, 12 sit just before a function's closing `}` and return by luck.
* Fix 1 (new patch `0009`): a `j` to an import always emits `return;`; other tail-call paths using the same condition (conditional-branch tails, ...) are checked too. `0005` stays equal to PR #37.
* Fix 2 (decided after looking): find why import stub `0x088C0540` is in the function list (possibly `0007`'s lui+addiu scan seeding a stub address, **inferred**); if our patch is the cause, filter stubs there (`is_import_stub`, as `0008` does).
* Check: all 13 sites have `return;` in the generated code, `lift_audit.py`, the reDMP1 comparison (including whether it has the same defect; read only), frames presented and the next stop in the headless run.
