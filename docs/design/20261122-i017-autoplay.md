# 설계: OSD에서 켜는 자동 플레이 (issue #17)

## 1. 요구사항

* 사용자 요청(2026-11-22): reDMP1처럼 OSD 메뉴에서 자동 플레이를 고를 수 있게 한다.
* 기준 구현은 [reDMP1 #59](https://github.com/reexec/reDMP1/issues/59)(v0.0.30)다. 로컬 `E:\MYWORK\Projects\reexec\reDMP1`의 `docs/design/20261121-i059-autoplay.md`, `docs/work-logs/20261121-i059-autoplay.md`, `src/app/autoplay.{h,cpp}`, `src/app/autoplay_probe.cpp`, 커밋 `d026d64`를 참고한다.
* 동작과 메뉴는 reDMP1과 같다.
  * Input 탭 맨 위에 `Autoplay` 체크박스와 설명 한 줄을 둔다.
  * 켜져 있고 플레이 장면이면 화면 오른쪽 위에 작은 `AUTOPLAY` 표시가 보인다. 메뉴가 닫혀 있어도 보인다.
  * 실행할 때마다 꺼진 상태로 시작하고, `redmp2.ini`에 저장하지 않는다.
  * `--autoplay` 명령줄 옵션으로도 켤 수 있다.
  * 자동 플레이로 낸 점수도 평소처럼 저장된다. reDMP1에서 사용자가 정한 것과 같다.

## 2. 방식 (reDMP1과 같음)

* 입력 단계 자동 플레이다. 게임 코드는 고치지 않는다.
  * repsp `repsp::hle::ctrl::SetButtonFilter`(v0.0.29부터 있음)로 게임에 돌려줄 버튼을 바꾼다.
  * 노트가 판정선에 오는 프레임에 그 레인의 PSP 버튼을 누른 것으로 만든다. 판정, 점수, 키음, 화면은 게임이 처리한다.
* 필터의 규칙:
  * 플레이 장면에서만 동작한다.
  * 사람의 레인 버튼은 지우고, 나머지(START 등)는 둔다.
  * 레인마다 커서를 둔다. 노트 시각 t가 `now + d/2` 이하이면 누른다. d는 지난 호출과의 `now` 차이다.
  * 단타는 다음 호출에 반드시 뗀다. 롱노트는 끝 시각까지 누른 채로 둔다.
  * 곡이 바뀌거나 장면을 벗어나면 커서를 초기화한다.
  * 읽은 값이 이상하면(주소 범위 밖, 레인 수 이상) 아무것도 하지 않는다.
* 게임 전용 상수는 `src/app/autoplay.cpp`의 한 네임스페이스(`autoplay_layout`)에 모은다. 각 상수에 근거(생성 코드 주소, 메모리 측정)를 주석으로 단다. repsp에는 게임 정보를 넣지 않는다.

## 3. 1단계: DMP2 분석 (먼저, 리뷰 후 2단계)

DMP2는 DMP1과 다른 실행 파일(`ET_EXEC`, 기준 `0x08804000`)이다. 주소는 모두 새로 찾는다. 같은 개발사의 후속작이므로 reDMP1 설계 §2의 구조(오프셋 관계)를 가설로 삼되, 모두 DMP2에서 확인한다.

찾을 것(reDMP1 설계 §2.1–2.2와 같은 항목):

1. **패드**: `sceCtrlReadBufferPositive`의 버퍼 주소. 게임이 현재 버튼과 이전 버튼을 두는 곳.
2. **버튼 → 레인**: PSP 버튼 비트를 레인 비트로 바꾸는 함수와, 그것이 읽는 배치·옵션 값. 4B 외에 DMP2에 있는 모드(6B, 8B 등)의 배치 표.
3. **판정**: 레인별로 "방금 눌림"을 보고 판정하는 함수.
4. **장면과 객체**:
   * 현재 장면 전역과 플레이 장면 식별 방법(vtable 등)
   * 판정 객체: 레인 수, 레인별 채보 채널, 레인 비트
   * 점수 객체와 현재 채보 시각
   * 채보 객체
5. **노트 형식**: 채널의 노트 배열(시작·끝), 노트 원소, 노트의 시각·종류·채널, 롱노트의 길이와 판별 방법. reDMP1에서는 `+14` u16 길이가 7 이상이면 롱노트였다.

방법:

* 생성 코드(`src/game/dmp2/recomp/generated/`)를 읽는다. 버튼 비트 상수(`0x10`, `0x20`, `0x80`, `0x100`, `0x200`, `0x1000`, `0x2000`, `0x8000`)를 함께 쓰는 함수, `sceCtrlReadBufferPositive`를 부르는 곳을 찾는다.
* 플레이 중 게스트 메모리를 측정한다. 필요하면 이 저장소에 선택 사항(기본 꺼짐) 진단 환경 변수를 둔다. 예를 들어 지정한 vblank에 게스트 메모리 범위를 파일로 쓰는 것이다(`REDMP2_TRACE_NID`와 같은 방식). 출력은 저장소 밖에 둔다.
* 결과는 `docs/analysis/autoplay.md`(한국어 먼저, 영어 아래)에 쓴다. 항목마다 "확인됨 / 추정"과 근거(생성 코드 주소, 측정값)를 단다.
* **1단계가 끝나면 멈추고 보고한다.** 리뷰어가 분석을 검토한 뒤 2단계를 진행한다.

## 4. 2단계: 구현

1. `src/app/autoplay.{h,cpp}`: reDMP1의 구조를 가져오고 `autoplay_layout`을 DMP2 값으로 채운다. 노트 종류나 모드가 reDMP1과 다르면 그 차이만 바꾼다.
2. `src/app/autoplay_probe.cpp`와 CMake 등록: 합성한 게스트 메모리로 검사한다.
   * 비플레이 장면에서는 손대지 않는다.
   * DMP2의 모드별 배치가 맞다.
   * 단타는 한 번 누르고 다음 호출에 뗀다.
   * 연속 노트가 각각 눌린다.
   * 롱노트는 끝까지 누른다.
   * 사람의 레인 버튼은 지우고, START는 둔다.
3. `src/app/settings_ui.{h,cpp}`: Input 탭의 `Autoplay`와 `AUTOPLAY` 표시.
4. `src/app/main.cpp`: `--autoplay`와 `SetButtonFilter` 연결, 종료 경로에서 해제.
5. `README.md`: 한국어·영어 설명.

## 5. 검증

1. probe가 통과한다. CTest: 생성 코드 없이 Win64 Debug/Release, 생성 코드 포함 Release. Linux는 CI.
2. 게임(FFmpeg 플러그인 Release 빌드, `--autoplay`, 입력 스크립트로 곡에 들어감):
   * 한 곡을 끝까지 진행해 결과 화면에 닿는다.
   * 미스(BREAK) 0, 콤보가 노트 수와 같다.
   * 롱노트가 있으면 롱노트도 성공이다.
   * 디스패치 미스 0
   * 결과 화면은 덤프로 확인하고, 덤프는 커밋하지 않는다.
3. 4B 말고 다른 모드도 한 곡씩 확인한다. 들어갈 수 있는 모드만 대상이다.
4. 사용자가 창 모드에서 OSD로 켜고 끄며 확인한다.

# Design: autoplay toggled from the OSD (issue #17)

## 1. Requirements

* User request (2026-11-22): make autoplay selectable from the OSD menu, as in reDMP1.
* The reference implementation is [reDMP1 #59](https://github.com/reexec/reDMP1/issues/59) (v0.0.30). In the local `E:\MYWORK\Projects\reexec\reDMP1`, see:
  * `docs/design/20261121-i059-autoplay.md`
  * `docs/work-logs/20261121-i059-autoplay.md`
  * `src/app/autoplay.{h,cpp}`, `src/app/autoplay_probe.cpp`
  * commit `d026d64`
* Behaviour and menu are the same as reDMP1:
  * An `Autoplay` checkbox with a one-line description at the top of the Input tab.
  * While it is on and the play scene is active, a small `AUTOPLAY` badge shows at the top right, even with the menu closed.
  * Off at each start; not saved to `redmp2.ini`.
  * Also enabled by the `--autoplay` command-line option.
  * Scores from autoplay are saved as usual, as the user decided for reDMP1.

## 2. Approach (same as reDMP1)

* Input-stage autoplay; the game code is not changed.
  * repsp `repsp::hle::ctrl::SetButtonFilter` (available since v0.0.29) changes the buttons returned to the game.
  * On the frame a note reaches the judgement line, the filter presses that lane's PSP button. The game handles judgement, score, key sounds and the screen.
* Filter rules:
  * It acts only in the play scene.
  * Human lane buttons are cleared; others (START etc.) are kept.
  * Each lane has a cursor. A note at time t is pressed when t ≤ `now + d/2`, where d is the change in `now` since the last call.
  * A tap note is always released on the next call. A long note is held until its end time.
  * Cursors reset on a song change or on leaving the scene.
  * If a value read looks wrong (address out of range, impossible lane count), the filter does nothing.
* Game-specific constants live in one namespace (`autoplay_layout`) in `src/app/autoplay.cpp`. Each carries its evidence (generated-code address, memory measurement) as a comment. No game information goes into repsp.

## 3. Phase 1: DMP2 analysis (first; phase 2 after review)

DMP2 is a different executable from DMP1 (`ET_EXEC`, base `0x08804000`), so every address is found anew. It is a sequel by the same developer, so reDMP1 design §2's structure (the offset relationships) is a hypothesis, but everything is confirmed on DMP2.

What to find (the same items as reDMP1 design §2.1–2.2):

1. **Pad**: the `sceCtrlReadBufferPositive` buffer, and where the game keeps the current and previous buttons.
2. **Buttons → lanes**: the function that maps PSP button bits to lane bits, and the layout/option values it reads. Layout tables for DMP2's modes other than 4B (6B, 8B, ...).
3. **Judgement**: the function that judges each lane's "just pressed".
4. **Scene and objects**:
   * the current-scene global and how to identify the play scene (vtable or similar)
   * the judgement object: lane count, per-lane chart channels, lane bits
   * the score object and current chart time
   * the chart object
5. **Note format**: a channel's note array (start and end), the note element, a note's time, type and channel, and a long note's length and how it is told apart. In reDMP1, a long note was a `+14` u16 length of 7 or more.

Method:

* Read the generated code (`src/game/dmp2/recomp/generated/`). Look for functions that use the button bit constants together (`0x10`, `0x20`, `0x80`, `0x100`, `0x200`, `0x1000`, `0x2000`, `0x8000`), and for callers of `sceCtrlReadBufferPositive`.
* Measure guest memory during play.
  * If needed, add an optional (off by default) diagnostic environment variable to this repository, for example one that writes a guest memory range to a file at a given vblank (like `REDMP2_TRACE_NID`).
  * Output stays outside the repository.
* Write the results to `docs/analysis/autoplay.md` (Korean first, English below). Mark each item "confirmed / inferred" with its evidence (generated-code address, measured value).
* **Stop and report when phase 1 is done.** Phase 2 starts after the reviewer checks the analysis.

## 4. Phase 2: implementation

1. `src/app/autoplay.{h,cpp}`: take reDMP1's structure and fill `autoplay_layout` with DMP2 values. Change only what differs from reDMP1 (note types, modes).
2. `src/app/autoplay_probe.cpp`, registered in CMake, checks with synthetic guest memory:
   * no change outside the play scene
   * correct layouts for DMP2's modes
   * a tap note is pressed once and released on the next call
   * consecutive notes are each pressed
   * long notes are held to the end
   * human lane buttons are cleared and START is kept
3. `src/app/settings_ui.{h,cpp}`: the Input tab `Autoplay` checkbox and the `AUTOPLAY` badge.
4. `src/app/main.cpp`: `--autoplay`, hooking up `SetButtonFilter`, and clearing it on exit paths.
5. `README.md`: Korean and English descriptions.

## 5. Verification

1. The probe passes. CTest: Win64 Debug/Release without generated code, and Release with it. Linux in CI.
2. Game (FFmpeg-plugin Release build, `--autoplay`, an input script to enter a song):
   * one song runs to its result screen
   * no misses (BREAK 0), and the combo equals the note count
   * long notes, if present, also succeed
   * no dispatch miss
   * the result screen is checked from a dump; dumps are not committed
3. One song in each mode other than 4B, where that mode can be entered.
4. The user turns it on and off from the OSD in windowed mode.
